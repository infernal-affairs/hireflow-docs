# 从项目需求到数据库建表：可复用分析手册

> 适用场景：拿到一个业务项目后，先分析领域与数据关系，再设计数据库和 SQL。
>
> 本文不是“所有项目都照抄”的模板，而是一套判断顺序和检查方法。

## 一、总体原则

数据库设计不是先打开编辑器写 `CREATE TABLE`，而是按下面的顺序推进：

```text
理解业务目标
→ 找业务对象
→ 找对象关系
→ 定义业务规则
→ 确定字段和约束
→ 设计索引
→ 写 SQL
→ 用真实场景验证
```

核心原则：

1. 先找业务对象，再找表。
2. 按字段是否一定存在拆表，不按页面拆表。
3. 能由数据库保证的完整性约束，不只依赖 Java 判断。
4. 展示值和比较值分开。
5. 当前业务优先，不为想象中的需求过度设计。
6. 先写清业务规则，再决定字段、外键和唯一约束。

## 二、第一步：明确业务闭环

先写清楚系统最核心的完整动作，而不是先列功能清单。

例如 HireFlow：

```text
招聘方发布职位
→ 求职者完善资料并投递
→ 招聘方查看投递并推进状态
→ 求职者查看进度
```

从闭环中可以提取出：

```text
参与者：求职者、招聘方
对象：公司、职位、投递
动作：发布、投递、处理、查看
状态：上架/下架、待筛选/面试中/录用/拒绝
```

判断标准：

- 没有这个对象，闭环还能完成吗？
- 没有这个关系，历史还能追溯吗？
- 没有这个状态，业务规则还能表达吗？

## 三、第二步：从业务名词中找实体

不要按页面找表。

错误思路：

```text
登录页表
首页表
职位详情页表
```

正确思路：

```text
用户
求职者资料
公司
公司成员
职位
投递
```

每个实体先回答：

| 问题 | 作用 |
| --- | --- |
| 它独立存在吗？ | 判断是否需要独立表 |
| 它是某个对象独有的属性吗？ | 判断是否拆分还是一对一子表 |
| 它和别的对象是一对一、一对多还是多对多？ | 判断主键、外键和中间表 |
| 它是否需要保留历史？ | 判断快照、状态和删除策略 |

## 四、第三步：判断表之间是什么关系

先判断基数，再决定主键和外键。关系不清楚时，字段和外键一定会反复修改。

### 1. 一对一

判断标准：

> 父表的一条记录，是否最多只对应子表的一条记录？

例如：

```text
一个用户最多一份求职者资料
```

设计方案之一：

```text
candidate_profiles.user_id 同时是主键和外键
```

适用条件：

- 子对象对父对象最多一条
- 子对象的 ID 没有独立业务意义
- 不需要保留多个版本

### 2. 一对多

判断标准：

> 父表的一条记录，是否可以对应子表的多条记录？

例如：

```text
一家公司可以有多个职位
一个职位可以有多条投递
```

父表使用主键：

```text
companies.id
```

子表保存外键：

```text
jobs.company_id
applications.job_id
```

子表外键通常不唯一。

### 3. 多对多

判断标准：

> 两边是否都可以对应对方的多个记录？

例如：

```text
一个用户可以加入多个公司
一个公司可以有多个招聘方
```

需要中间表：

```text
company_members(company_id, user_id, ...)
```

并在组合上建立唯一约束：

```text
UNIQUE (company_id, user_id)
```

## 五、第四步：逐个确定字段

对每个字段回答六个问题：

1. 它表示什么业务事实？
2. 它是否必须存在？
3. 它是否必须唯一？
4. 它的合法值范围是什么？
5. 它是否会变化？
6. 它是当前值还是历史快照？

### 字段设计检查表

不要机械地对每个字段都加约束，而是先判断业务规则。

| 判断 | 约束 |
| --- | --- |
| 必须有值 | `NOT NULL` |
| 不能重复 | `UNIQUE` |
| 只能取固定值 | `CHECK` |
| 引用其他表 | `FOREIGN KEY` |
| 经常筛选、排序或连接 | `INDEX` |
| 省略时应有默认值 | `DEFAULT` |
| 需要解释用途 | `COMMENT` |

不要为了“看起来严谨”给所有字段都加唯一约束。

例如：

- 用户姓名可以重复，不应加 `UNIQUE`
- 公司展示名称可以变化，不一定唯一
- 公司归一化名称用于判重，需要唯一
- 职位标题可以重复，不应加 `UNIQUE`

## 六、第五步：主键怎么选

### 优先使用代理主键

代理主键是没有业务含义、只用于唯一标识记录的 ID。

大多数业务表使用：

```sql
id BIGINT UNSIGNED NOT NULL AUTO_INCREMENT
```

原因：

- 数字主键稳定
- 不随业务名称变化
- 外键引用简单
- 索引效率好

### 什么时候使用业务字段做主键

只有业务字段本身稳定、唯一、非空时才可以考虑。

例如：

- 国家代码
- ISBN

邮箱一般适合唯一键，不一定适合作为主键，因为邮箱可能变更。

### 什么时候使用共享主键

共享主键是把父表主键同时作为子表主键，用来表达一对一关系：



```sql
candidate_profiles.user_id PRIMARY KEY
```

### 什么时候使用联合主键

组合天然唯一时可以使用：

```sql
company_members(company_id, user_id) PRIMARY KEY
```

但如果有独立业务 ID 或后续需要单独引用某条关系，使用独立 `id` + 联合唯一约束往往更灵活。

## 七、第六步：外键怎么选

外键的选择原则：

先确认“子表是否真的需要指向父表的具体一行”，再决定字段和约束。

1. 子表确实需要指向父表的一条具体记录。
2. 引用父表主键或稳定的唯一键。
3. 子表和父表字段类型一致。
4. 根据业务决定 `NOT NULL`。
5. 根据关系基数决定是否唯一。
6. 根据生命周期决定 `RESTRICT`、`CASCADE` 或 `SET NULL`。
7. 根据查询场景为外键列设计索引。

### 外键字段是否唯一

- 一对多：不唯一
- 一对一：主键或唯一索引
- 多对多：中间表联合唯一

### 外键字段是否非空

- 必须关联：`NOT NULL`
- 可选关联：允许 `NULL`

### 删除策略选择

| 策略 | 适用情况 |
| --- | --- |
| `RESTRICT` | 历史数据必须保留，父记录不应随意删除 |
| `CASCADE` | 子记录没有独立生命周期 |
| `SET NULL` | 关系可选，父记录删除后允许失去关联 |

HireFlow 默认使用 `RESTRICT`，因为职位、投递、公司成员等历史数据需要保留。

## 八、第七步：唯一性怎么设计

### 单字段唯一

```text
users.email
companies.normalized_name
```

### 联合唯一

```text
applications(job_id, candidate_id)
```

表示同一求职者对同一职位只能投递一次。

### 展示值和比较值分离

例如公司：

```text
display_name      用户看到的名称
normalized_name   去空格、统一大小写后的判重名称
```

唯一约束加在归一化字段上。

注意：

- Java 判重负责友好提示
- 数据库唯一索引负责并发下最终防重
- 不能只靠“先查询，再插入”，因为并发时可能同时通过查询

## 九、第八步：索引怎么考虑

索引来自明确查询场景，不是字段越多越好。

先列出高频查询：

```text
按邮箱查用户
按状态和更新时间查职位
按公司查职位
按职位和状态查投递
```

再为这些查询设计索引。

引入索引时要考虑：

- 查询是否真的高频
- 索引列顺序是否匹配过滤条件
- 是否与现有索引重复
- 写操作是否会因此变慢

不要在没有查询场景时盲目加索引。

## 十、第九步：时间字段和状态字段

### 时间字段

常用：

```sql
created_at DATETIME(3) NOT NULL DEFAULT CURRENT_TIMESTAMP(3)
updated_at DATETIME(3) NOT NULL DEFAULT CURRENT_TIMESTAMP(3)
    ON UPDATE CURRENT_TIMESTAMP(3)
```

需要考虑：

- 是否需要毫秒
- 是否需要软删除时间
- 是否需要业务时间，例如投递时间、状态变更时间
- 是否需要历史操作日志

### 状态字段

状态不要只存“当前值”而不考虑流转规则。

需要明确：

```text
允许哪些状态
初始状态是什么
允许哪些转换
哪些是终态
谁可以修改
是否保留历史
```

数据库可以用 `CHECK` 限制取值，但复杂状态流转通常由 Service 层控制。

## 十一、第十步：历史和快照

要区分：

```text
当前事实
历史事实
```

例如：

- 用户当前姓名存在 `users.name`
- 投递时的姓名快照存在 `applications.candidate_name`

为什么不能只存 `candidate_id`？

因为用户后来修改姓名时，历史投递不应变化。

判断是否需要快照：

- 这个值未来可能变化吗？
- 历史记录需要保留当时的版本吗？
- 查询历史时是否需要显示旧值？

## 十二、第十一步：软删除与物理删除

本项目基本策略：

- 职位不物理删除，只切换上下架状态
- 成员移除使用状态和移除时间
- 投递记录永久保留
- 用户和公司是否删除应谨慎设计

判断：

| 需求 | 方案 |
| --- | --- |
| 需要恢复或审计 | 软删除或状态字段 |
| 没有历史价值 | 可以物理删除 |
| 删除父记录会影响历史 | 使用 `RESTRICT` 或软删除 |
| 子记录随父记录消失 | 可以使用 `CASCADE` |

不要默认所有表都加 `deleted_at`，先看是否真的需要恢复和审计。

## 十三、第十二步：SQL 落地顺序

建表顺序必须满足外键依赖：

```text
1. 无外键依赖的基础表，例如 users
2. 依赖基础表的子表，例如 candidate_profiles、companies
3. 依赖公司和用户的成员表
4. 依赖公司的职位表
5. 依赖职位和用户的投递表
```

文件职责建议分开：

```text
00-create-databases.sql   创建数据库
schema.sql                表、索引、约束
data.sql                  演示数据
```

开发阶段如果表结构频繁变化且没有数据，可以：

```sql
DROP TABLE IF EXISTS 子表;
DROP TABLE IF EXISTS 父表;
```

然后重新执行建表脚本。

有数据后应使用：

```sql
ALTER TABLE ...
```

不能随意删表。

## 十四、第十三步：验证设计

建表后至少验证：

1. 表能按顺序创建。
2. 外键能正确拒绝不存在的父记录。
3. 唯一约束能拒绝重复数据。
4. `CHECK` 能拒绝非法状态。
5. 删除父记录时行为符合业务规则。
6. 关键查询有合理索引。
7. 手动插入一组最小数据，验证关系是否成立。

建议检查命令：

```sql
-- 查看已创建的表。
SHOW TABLES;

-- 查看表的完整结构、外键和唯一约束。
SHOW CREATE TABLE 表名\G

-- 查看索引。
SHOW INDEX FROM 表名;
```

## 十五、HireFlow 的实际推导示例

### 需求

招聘方创建公司、发布职位；求职者投递；招聘方处理投递。

### 实体

```text
用户、求职者资料、公司、公司成员、职位、投递
```

### 关系

```text
用户 1:0..1 求职者资料
用户 N:M 公司（通过 company_members）
公司 1:N 职位
职位 1:N 投递
求职者 1:N 投递
同一求职者对同一职位最多一条投递
```

### 关键约束

```text
users.email UNIQUE
companies.normalized_name UNIQUE
applications(job_id, candidate_id) UNIQUE
```

### 关键快照

```text
applications.candidate_name
applications.candidate_email
applications.skills
applications.bio
```

### 关键历史规则

```text
职位只下架，不物理删除
投递记录永久保留
OFFERED 和 REJECTED 是终态
```

## 十六、设计时常见误区

### 误区 1：一个页面一张表

页面是展示方式，不是领域模型。

### 误区 2：所有关联都建外键后，字段都必须唯一

错误。一对多关系的外键通常可重复。

### 误区 3：只靠 Java 判重

并发时仍可能重复写入。数据库唯一约束是最后防线。

### 误区 4：展示名称和判重名称混在一起

展示需要保留原始写法，判重需要统一规则。

### 误区 5：为了未来可能的需求过度拆表

如果当前明确是一对一，先用共享主键；当业务真的支持多版本时再迁移。

### 误区 6：所有字段都允许 `NULL`

`NULL` 会让查询和业务判断复杂。非必填字段才考虑 `NULL`。

### 误区 7：所有删除都使用 `CASCADE`

可能误删历史数据。涉及业务审计和历史记录时优先 `RESTRICT` 或状态字段。

## 十七、面试表达模板

可以按下面顺序讲数据库设计：

1. 先说明核心业务闭环。
2. 列出核心实体和关系。
3. 说明主键和外键选择。
4. 说明唯一约束和业务规则。
5. 说明索引与查询场景。
6. 说明状态、快照和历史保留策略。
7. 说明哪些规则由数据库保证，哪些必须由 Service 保证。

## 十八、最小检查清单

- [ ] 核心业务闭环是否清楚
- [ ] 每个实体是否必要
- [ ] 每张表是否有主键
- [ ] 关系基数是否明确
- [ ] 外键字段类型是否一致
- [ ] 外键是否非空、是否唯一是否已判断
- [ ] 删除和更新行为是否明确
- [ ] 业务唯一性是否用唯一索引兜底
- [ ] 状态取值是否有约束
- [ ] 必要的历史快照是否保存
- [ ] 索引是否有真实查询场景
- [ ] 建表顺序是否满足外键依赖
- [ ] 是否能在干净数据库中从头执行
